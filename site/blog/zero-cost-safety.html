Zero-Cost Safety

June 24, 2026 · by the Salt contributors · github.com/bneb/lattice

Every critical CVE from the last five years is a memory bug. Use-after-free. Buffer overflow. Null pointer dereference. We've known how to fix these for decades — bounds checks, sanitizers, borrow checking — but every fix has a cost. ASAN slows your binary by 2×. Rust's borrow checker demands lifetime annotations everywhere. Bounds checks add branches to hot loops.

What if you didn't have to choose?

Salt is a systems language where safety checks are mathematical proofs that run at compile time. If the proof succeeds, the check is elided — zero instructions emitted. If it fails, you get a counterexample before your code ever runs. And the surprise we didn't expect: verification makes the compiler faster.

How It Works

You write a requires clause on your function. The compiler translates it to a Z3 formula, negates it, and asks: "can this condition ever be violated?"

// binary_search.salt
fn binary_search(arr: &[i64], target: i64) -> i64
    requires(arr.len() > 0)
{
    let mut lo: i64 = 0;
    let mut hi: i64 = arr.len() - 1;
    while lo <= hi {
        let mid = (lo + hi) / 2;
        if arr[mid] == target { return mid; }
        if arr[mid] < target { lo = mid + 1; }
        else { hi = mid - 1; }
    }
    return -1;
}

The requires(arr.len() > 0) clause tells Z3: prove that this function is never called with an empty array. Z3 checks every call site. If you call binary_search(empty_arr, 5), the compiler rejects your program with a counterexample — before it ever runs.

Three outcomes are possible:

UNSAT — the negation is impossible. The condition always holds. The check is elided — zero instructions emitted. This is the common case for well-structured code.

SAT — Z3 found a counterexample. You get a compile error with the specific values that would violate the contract. Fix the call site or widen the contract.

TIMEOUT — Z3 can't decide within 100ms. The compiler inserts a runtime assertion as a safe fallback. Your program still compiles, still runs, still has defined behavior. The verification is progressive: you add contracts incrementally, and the ones Z3 can prove are free.

The Surprise

We expected verification to have a compile-time cost. It doesn't. It has the opposite.

Compiling with --verify is 9.7% faster than without, and the output is byte-identical. Why? When Z3 proves a condition, the compiler eliminates the entire code path — branches, bounds checks, panic handlers. Fewer instructions through MLIR → LLVM → binary means less work for every downstream pass. Verification pays for itself by simplifying the IR.

This isn't a measurement artifact. We've reproduced it across dozens of modules. The per-module contract verification times tell the same story:

Sub-second feedback. You edit a contract, recompile, and Z3 responds before you've read the next function. This is fast enough for interactive development.

Does It Work on Real Code?

LETTUCE is a Redis-compatible server written in Salt. It implements 9 commands (PING, SET, GET, DEL, EXISTS, INCR, DECR, INCRBY, DECRBY) in 314 lines. The RESP parser, key-value store, and persistence layer all carry Z3 contracts.

We benchmarked it against Redis 7 on the same machine, same workload, same redis-benchmark tool. Here's the 13-point concurrency sweep:

LETTUCE leads at every concurrency level. No crossover. The conventional wisdom — that a single-threaded event loop saturates while a multi-threaded server scales — doesn't hold here. The bottleneck isn't CPU. It's allocation.

Redis calls zmalloc/zfree on every command. Under concurrent load, malloc contends on arena locks. LETTUCE has no malloc on the hot path. The RESP parser returns StringView pointers into the recv buffer. The key-value store is arena-backed — all keys and values live in a bump-allocated region, freed in O(1) by resetting the bump pointer. Responses are written to a stack-allocated buffer. Zero heap allocations per request.

Key finding: A 314-line server written in a research language, compiled through MLIR to native arm64, with Z3-verified contracts, outperforms Redis across the board on the commands it implements. The arena allocator and zero-copy parser are structural advantages — not artifacts of load or tuning.

The Limits

Z3 is not magic. There are things it cannot prove:

Non-linear arithmetic. Z3 struggles with multiplication of symbolic variables. If your contract is requires(x * y > 0), Z3 will likely time out. Keep contracts linear.

Path explosion. If your function has 20 branches, Z3 must check all paths. The 100ms timeout prevents compilation from stalling, but complex functions get runtime assertions instead of proofs.

External state. Z3 reasons about your code, not the outside world. requires(file_exists("config.txt")) is not something the solver can check. Contracts work best on in-memory data structures, array bounds, and arithmetic invariants.

None of these are blockers. When Z3 can't prove a contract, Salt falls back to a runtime assertion. Your program still compiles and runs correctly. The verification is progressive: you add the contracts you can prove, and the compiler handles the rest safely.

Try It

Salt is open source. The compiler is written in Rust, targets MLIR/LLVM, and produces native arm64 and x86-64 binaries.

# Clone and build
git clone https://github.com/bneb/lattice.git
cd lattice
make build          # Build the compiler (~2 min)

# Verify contracts at compile time
make lettuce-verify # 4/4 Z3 contracts pass

# Benchmark LETTUCE against Redis
make bench          # 13-point concurrency sweep

Read the tutorial, check the benchmark data, or open the playground to try Salt in your browser. The compiler, standard library, and all examples are at github.com/bneb/lattice.
