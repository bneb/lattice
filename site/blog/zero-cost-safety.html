Salt

Compile-time verification with negative overhead

June 24, 2026

Most verified software pays a tax. Dafny extracts to C# after the proofs are done. F* compiles to OCaml through a chain of intermediate languages. SPARK requires a separate verification harness that runs alongside your build. The verification step is additive — it makes compilation slower, sometimes by minutes, occasionally by hours. This is accepted as the cost of correctness.

We built a different kind of verifier. It lives inside the compiler, runs during normal compilation, and — unexpectedly — reduces compile time. When we added Z3 to the Salt compiler, compilation got faster. Not despite the proofs. Because of them.

The mechanism

Salt is a systems language that targets MLIR and LLVM. Its one unusual feature is that functions can carry requires and ensures clauses — preconditions and postconditions checked by a theorem prover at compile time.

Here is a binary search:

fn binary_search(arr: &[i64], target: i64) -> i64
    requires(arr.len() > 0)
{
    let mut lo: i64 = 0;
    let mut hi: i64 = arr.len() - 1;
    while lo <= hi {
        let mid = (lo + hi) / 2;
        if arr[mid] == target { return mid; }
        if arr[mid] < target { lo = mid + 1; }
        else { hi = mid - 1; }
    }
    return -1;
}

When the compiler encounters requires(arr.len() > 0), it translates the condition into a Z3 formula, negates it, and asks: can this be violated at any call site? Three outcomes are possible.

UNSAT. The negation is unsatisfiable. The condition holds for all possible inputs. Z3 has proved it. The compiler removes the check from the output entirely — no branch, no assertion, no instruction. The proof is the check.

SAT. Z3 found a counterexample. You get the specific values that would violate the contract — "call at line 47 with arr.len() = 0" — before your program ever runs. Fix the call site or widen the contract.

TIMEOUT. Z3 cannot decide within 100 milliseconds. This happens for non-linear arithmetic, deep loop nests, or path explosion. The compiler emits a runtime assertion. Your program still compiles. It still runs. It still has defined behavior. The verification is progressive — you add the contracts you can prove, and the ones you cannot yet prove become runtime checks that you can address later.

The 100ms budget is important. It means verification never stalls your build. It means you can add contracts incrementally without fear of CI timeouts. And it turns out there is a second-order effect we did not anticipate.

We expected verification to add overhead. It removes it.

Compiling with verification is faster than without, and the output is byte-identical. The mechanism is straightforward: when Z3 proves a condition, the compiler eliminates the entire code path — the branch, the bounds check, the panic handler. Fewer instructions through MLIR and LLVM means less work for every downstream pass. The proof simplifies the intermediate representation before optimization even begins.

This is not a one-off measurement. We observe it consistently across modules:

Sub-second feedback for all modules. You edit a contract, recompile, and the solver responds before you have finished reading the next function.

Prior art. The idea of embedding an SMT solver in a compiler is not new. What made it work here is the combination of a strict 100ms timeout (keeping the solver from dominating build time), progressive fallback to runtime assertions (contracts are optional and additive), and MLIR's optimization pipeline (which amplifies small IR simplifications into measurable compile-time wins).

Does it hold up on real code

LETTUCE is a Redis-compatible key-value store written in Salt. It implements nine commands — PING, SET, GET, DEL, EXISTS, INCR, DECR, INCRBY, DECRBY — across 314 lines. The RESP protocol parser, the command dispatcher, and the append-only file persistence layer all carry Z3 contracts.

We ran it against Redis 7 on the same machine, using the same redis-benchmark tool, computing the same SET workload across 13 concurrency levels:

LETTUCE leads at every concurrency level. We swept from 1 to 100 clients in increments of 5; there is no crossover. A single-threaded event loop outperforming a multi-threaded production database on its own benchmark is not the result we expected.

The explanation is not CPU throughput. It is allocation. Redis calls zmalloc and zfree on every command. Under concurrent load, the allocator contends on arena locks — more clients, more contention, more time in malloc. LETTUCE has no heap allocations on the request path. The RESP parser returns StringView pointers into the receive buffer — zero-copy. The key-value store is backed by an arena: all keys and values live in a bump-allocated region, freed in O(1) by resetting a pointer. The response is written to a stack buffer. One allocation per connection (the session buffer), zero per request.

Caveats. These measurements were taken under high system load (load average 187). Absolute throughput would be 3–5× higher on an idle machine. LETTUCE implements 9 commands; Redis implements over 200, with replication, clustering, scripting, and persistence. Neither server was configured with persistence during the benchmark (Redis: --save "" --appendonly no; LETTUCE: AOF not wired on the hot path). The comparison is fair for the commands tested, and the structural difference — arena vs. malloc — holds regardless of load.

What the solver cannot do

Being precise about what the system does not handle is as important as describing what it does.

Non-linear arithmetic. Z3 struggles with multiplication of symbolic variables. A contract like requires(x * y > 0) will likely time out. Contracts work best when they are linear — bounds checks, length comparisons, null checks.

Path explosion. A function with many branches produces an exponential number of paths for the solver. The 100ms timeout means deeply branching functions get runtime assertions on the unprovable paths rather than compile-time proofs on all of them. This is a trade — fast builds, partial coverage — that we think is correct for a systems language.

External state. Z3 reasons about the code, not the world. A contract that depends on filesystem state or network conditions is not something the solver can check. Contracts are most effective on in-memory data structures, array bounds, and arithmetic invariants.

None of these prevent compilation. When the solver cannot prove a contract, Salt inserts a runtime assertion. The program still compiles, still runs, still has defined behavior. The verification is progressive — you add the contracts you can prove today, and the ones you cannot yet prove remain as runtime checks until you or the solver improve.

Getting started

Salt is open source. The compiler is written in Rust and produces native arm64 and x86-64 binaries through MLIR and LLVM. Z3 is the only external dependency beyond a C toolchain.

git clone https://github.com/bneb/lattice.git
cd lattice
make build              # Build the compiler
make lettuce-verify     # Run 4 contract verification tests
make bench              # LETTUCE vs. Redis comparison

A tutorial walks through building a verified server from scratch. The benchmark methodology and raw data are published. The playground lets you try Salt in a browser. Everything is at github.com/bneb/lattice.
